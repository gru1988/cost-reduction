# Задание 1. Матрица Sourcing Strategy (Buy vs Build)

Матрица распределяет все L2-возможности с карты (`capability_map_heatmap.png`) по стратегиям поставки.
Визуальное представление — `sourcing_quadrant.png`, та же таблица с фильтрами — `sourcing_matrix.xlsx`.

## Принципы выбора

| Стратегия | Когда применяем |
|---|---|
| **Buy (SaaS)** | Типовая функция рынка (касса, лояльность, фискализация, MDM устройств). Своя разработка не даёт преимущества, а держит TCO на высоком уровне. |
| **Buy (PaaS)** | Инфраструктурный строительный блок (брокер сообщений, iPaaS, хранилище данных). Берём управляемый сервис, не администрируем сами. |
| **Build на PaaS** | Логика, специфичная для VitaStore и влияющая на скорость M&A (онбординг, SKU Matching, распространение цен). Код и правила — свои, инфраструктура и ML-модели — облачные сервисы. |
| **Build** | Небольшие доработки, которых нет на рынке в нужном виде (офлайн-стратегия, чек-лист due diligence). |
| **Keep** | Работает приемлемо или дифференцирует (SAP ERP, Promo Engine, Smart Fulfillment). Не переписываем, открываем API. |
| **Retire** | Функция исчезает вместе с локальными серверами (эксплуатация серверов, лицензии ОС/СУБД). |

Облачные сервисы выбираем у провайдеров с ЦОД в РФ: этого требует 152-ФЗ о персональных данных (данные участников программы лояльности).

## Выводы

1. **Главный источник TCO — кассовая зона магазина** (3.1, 3.2, 6.1, 6.2): толстый клиент, локальный сервер и лицензии в каждом из 500+ магазинов. Покупаем Cloud POS как SaaS, локальную инфраструктуру выводим.
2. **Главный источник ручного труда — интеграция купленных сетей** (1.3, 2.2): сопоставление номенклатуры вручную занимает до двух недель. Это специфичная для VitaStore функция, от которой зависит темп M&A. Строим собственный конвейер онбординга и ИИ-маппинга на облачных PaaS/ML-сервисах (см. Task2).
3. **Блокер стандартизации — разнородное оборудование** (3.2, 3.3, 6.4): решается слоем абстракции (HAL-агент + Payment Gateway) и MDM, а не новой сборкой кассы под каждый терминал (см. Task3).
4. **SAP ERP, Promo Engine и Smart Fulfillment сохраняем**: они не главная причина затрат, а замена ERP — отдельный многолетний проект. Меняется только способ интеграции: файлы и FTP заменяются API и событиями.
5. **Расхождение в артефактах**: на вики-схеме (артефакт 1) указан real-time REST-обмен касса ↔ SAP. По регламенту (артефакт 2) и инцидентам (артефакт 3) фактически работает ночной FTP-обмен и ручной труд. Карта и матрица построены по фактическому состоянию.
