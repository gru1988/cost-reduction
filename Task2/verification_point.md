# Задание 2. Целевой процесс онбординга магазина (TO-BE)

Файлы:
- `onboarding_to_be.bpmn` — диаграмма в BPMN 2.0 (открывается в Camunda Modeler, bpmn.io, Bizagi и других редакторах);
- `onboarding_to_be.png` — та же диаграмма в виде картинки;
- этот файл — описание процесса и точки верификации.

## 1. Что меняется по сравнению с AS-IS

| | AS-IS (регламент, артефакт 2) | TO-BE |
|---|---|---|
| Сбор данных | Выезд ИТ-инженера, дамп CSV/XLS, отправка по email | Магазин сам загружает выгрузку через портал онбординга или утилиту-коннектор. Выезд не нужен |
| Очистка данных | Нет, грязные данные идут сразу в Excel | Автоматический парсинг, нормализация и DQ-проверка. При ошибках магазин получает отчёт и загружает исправленный файл |
| Сопоставление (маппинг) | VLOOKUP по штрихкодам, ~80% позиций вручную | ИИ-сервис: точное совпадение по GTIN/EAN, затем семантический поиск (эмбеддинги + LLM), confidence и бизнес-правила |
| Участие человека | Товаровед обрабатывает почти весь ассортимент | Товаровед разбирает только спорные позиции (около 10–15%) и проверяет выборку 3% автоматических решений |
| Загрузка в ERP | Ручная загрузка файла | Загрузка через API с проверкой мастер-данных в SAP |
| Доставка на кассу | XML по FTP в 02:00 на локальный сервер | Событие из SAP, Cloud POS получает каталог и цены дельтой |
| Приёмка | Нет. Ошибки находят покупатели на кассе (15% ошибок) | Автотест штрихкодов в Cloud POS и пробная продажа в магазине до открытия |
| Срок | 2–3 недели | ≤ 5 рабочих дней |

## 2. Пулы диаграммы

| Пул | Тип | Роль |
|---|---|---|
| Купленный магазин | Люди | Выгружает данные, подключает комплект Cloud POS, проводит пробную продажу |
| VitaStore HQ: менеджер интеграции | Люди | Запускает онбординг, принимает решение об открытии |
| VitaStore HQ: товаровед (Data Steward) | Люди | Точка верификации: проверяет спорные позиции, заводит новые SKU, делает аудит выборки |
| Платформа онбординга (iPaaS/ETL) | Система | Оркестрирует конвейер: парсинг, DQ-проверка, маршрутизация по confidence, сборка таблицы соответствий |
| ИИ-сервис SKU Matching | Система | Ищет кандидатов и считает уверенность |
| SAP ERP (MDM) | Система | Эталонный справочник и цены, финальная проверка мастер-данных |
| Cloud POS | Система | Разворачивает каталог в новом магазине и проводит автотест |

## 3. Поток данных при автоматическом маппинге

1. **Выгрузка магазина** (CSV / XLS / дамп БД старой кассы) поступает на платформу онбординга.
2. **Нормализация.** Приводим кодировку и единицы измерения («400», «400мл», «0,4 л» → 400 мл). Раскрываем сокращения («Шамп.» → «Шампунь», «д/рук» → «для рук»). Выделяем бренд по словарю синонимов («H&S» = «Head&Shoulders»). Проверяем контрольные цифры EAN-13.
3. **DQ-проверка**: дубли, пустые штрихкоды, нулевые и аномальные цены. Если ошибок больше порога, магазин получает отчёт и повторяет загрузку. Это петля на диаграмме.
4. **ИИ-сервис** обрабатывает пакет SKU в три шага:
   - **точное совпадение по GTIN/EAN** с эталонным каталогом VitaStore — самый надёжный путь, обычно закрывает большую часть позиций;
   - **семантический поиск** для позиций без совпавшего штрихкода. LLM разбирает название на атрибуты (бренд, линейка, тип, объём), по эмбеддингам из векторного индекса эталона выбираются топ-3 кандидата;
   - **скоринг**: итоговый confidence учитывает семантическую близость и совпадение атрибутов, затем проверяются бизнес-правила.
5. Результат (кандидаты + score) возвращается на платформу. Платформа разделяет пакет по порогам (inclusive gateway) на автоматическую и ручную ветки.
6. После верификации платформа собирает **таблицу соответствий** с аудит-логом: кто или что принял решение, с какой уверенностью, на основании чего. Решения товароведов попадают в обучающую выборку.
7. **SAP ERP** загружает соответствия и новые карточки, проверяет НДС, категорию и ценовую зону, публикует событие «каталог и цены магазина готовы».
8. **Cloud POS** загружает каталог и цены и проверяет, что каждый штрихкод из исходной выгрузки находится в каталоге.

## 4. Точка верификации: как участвует человек

### Пороги маршрутизации

| Уверенность ИИ | Что происходит | Кто решает |
|---|---|---|
| **≥ 95%** и все бизнес-правила пройдены | Автоподтверждение | Система. 3% случайной выборки уходит товароведу на аудит |
| **70–95%** или нарушено хотя бы одно правило (при любом confidence) | Задача в очереди верификации. Интерфейс показывает исходную позицию и топ-3 кандидата с фото, ценой и атрибутами. Товаровед выбирает кандидата одним кликом | Товаровед |
| **< 70%** или кандидата нет | Заявка на новую карточку SKU в MDM. Скорее всего, это новый для VitaStore товар | Товаровед |

### Жёсткие бизнес-правила (переводят позицию на ручную проверку при любом confidence)

- **Цена**: старая цена магазина отличается от цены кандидата больше чем на ±30%. Это прямо защищает от сценария из интервью, когда дешёвый штрихкод привязывают к дорогому крему и продают товар в минус.
- **Объём или вес** не совпадают («400 мл» против «200 мл»).
- **Бренд** не совпадает или не определён.
- **Категория** не совпадает (крем для рук против шампуня).
- **Конфликт штрихкода**: один штрихкод магазина претендует на два разных SKU VitaStore или наоборот.
- **Дорогие позиции** (например, дороже 3 000 ₽) и маркируемые товары проверяются по принципу «4 глаза», даже если уверенность высокая.

### Контроль качества автоматических решений

1. **Аудит выборки.** Товаровед проверяет случайные 3% автоподтверждённых позиций. Если в выборке ошибок больше 1%, порог автоподтверждения для этой сети повышается до 98%, а пакет перепроверяется.
2. **Калибровка порогов.** На первых 2–3 поглощениях работаем консервативно: автоподтверждение только от 98%. Пороги снижаем, когда фактическая точность (precision) на размеченных данных стабильно выше 99%.
3. **Обратная связь.** Каждое решение товароведа (подтвердил, исправил, отклонил) попадает в обучающую выборку и словарь синонимов. Следующие сети сопоставляются точнее, доля ручной работы снижается.
4. **Автотест в Cloud POS.** До открытия проверяется, что все штрихкоды из исходной выгрузки находятся в каталоге и имеют цену.
5. **Пробная продажа в магазине.** 20 случайных товаров пробиваются на кассе, ценники сверяются. Расхождения менеджер исправляет вместе с товароведом до открытия.
6. **Аудит-лог.** Для каждого соответствия хранится, кто или что его принял и с каким score. Если ошибка всплывёт после открытия, её можно найти и исправить точечно.

## 5. Оценка трудозатрат и сроков (магазин на 10 000 SKU)

Допущения: доли позиций — экспертная оценка для дрогери-ассортимента, их нужно уточнить на пилоте.

| Группа | Доля | Позиций | Норматив | Трудозатраты |
|---|---|---|---|---|
| Совпадение по штрихкоду + ИИ ≥ 95% | ~85% | 8 500 | авто | 0 ч (аудит 3% ≈ 255 позиций × 20 с ≈ 1,5 ч) |
| Верификация 70–95% | ~12% | 1 200 | ~30 с на позицию (выбор из топ-3) | ≈ 10 ч |
| Новые карточки < 70% | ~3% | 300 | ~3 мин на карточку | ≈ 15 ч |
| **Итого** | | | | **≈ 26 ч ≈ 3,5 рабочего дня одного товароведа** (или 2 дня на двоих) |

Сейчас при ручном просмотре ~80% ассортимента нужно 8 000 позиций × (1/500 ч) = 16 ч только по нормативу на сопоставление. На практике из-за грязных названий уходит до двух недель. Новый процесс снимает рутину: человек принимает решения только там, где ошибка стоит денег.

### План-график на 5 рабочих дней

| День | Что происходит |
|---|---|
| 1 | Регистрация магазина, выгрузка данных, DQ-проверка, автоматический маппинг (часы). Отправка комплекта Cloud POS |
| 2–3 | Верификация спорных позиций и заведение новых SKU товароведом. Магазин подключает планшет (zero-touch) |
| 4 | Загрузка в SAP, публикация в Cloud POS, автотест |
| 5 | Пробная продажа, исправление расхождений, открытие под брендом VitaStore |

## 6. Целевые метрики процесса

- Срок онбординга: **≤ 5 рабочих дней** (сейчас 2–3 недели).
- Доля позиций, сопоставленных автоматически: **≥ 80%** с первой сети, **≥ 90%** после накопления обучающей выборки.
- Ошибки сопоставления на кассе: **< 1%** (сейчас 15%).
- Выезды ИТ-инженера для переноса номенклатуры: **0**.
