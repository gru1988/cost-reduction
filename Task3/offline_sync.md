## 2. Переход от «толстого» клиента к cloud-native

| Слой | AS-IS | TO-BE |
|---|---|---|
| Кассовое приложение | Десктоп-приложение под Windows, установка инженером | **Web POS (PWA)** на планшете. Обновляется централизованно, ставится через MDM без выезда |
| Данные магазина | Локальный MS SQL / PostgreSQL на ПК в подсобке | **Облачная БД** (Managed PostgreSQL) + локальный кэш на планшете (IndexedDB/SQLite) только для офлайна |
| Оборудование | Драйверы внутри кассового приложения | **HAL Agent** — отдельный сервис на планшете с единым API и плагинами под вендоров + облачный **Payment Gateway** |
| Обмен с HQ | FTP в 02:00, email, Excel | **Event Bus (Kafka)** + Integration Layer: события и API в почти реальном времени |
| Поддержка | Выезд инженера, замена системного блока | Удалённый мониторинг (MDM). Сломался планшет — курьер привозит преднастроенный, замена за минуты |

Облачную инфраструктуру размещаем у провайдера с ЦОД в РФ: этого требует 152-ФЗ о персональных данных участников программы лояльности.

## 3. Слой абстракции оборудования (HAL / Payment Gateway)

Кассовое приложение из браузера не может обращаться к USB-портам, а парк оборудования в купленных магазинах разнородный. Поэтому вся работа с «железом» вынесена в два компонента.

**HAL Agent** — нативный сервис на планшете (Android). Он открывает для Web POS локальный API (`localhost`, REST/WebSocket) с операциями, не зависящими от вендора: `pay(amount)`, `refund()`, `printReceipt(check)`, `openShift()`, `closeShift()`, `scan()`. Внутри работают **плагины-адаптеры**: Sber (ARCUS-2), Альфа-Банк, Ingenico, Verifone для терминалов; АТОЛ, Штрих-М и другие для ККТ; сканеры и весы. Плагин переводит единый вызов в протокол конкретного устройства (USB, Bluetooth, LAN).

**Payment Gateway** (облачная платёжная оркестрация) скрывает различия эквайеров на стороне облака. Он маршрутизирует облачные и QR-платежи (СБП), регистрирует транзакции из HAL и сверяет их с эквайерами. Касса знает один платёжный API, а не протокол каждого банка.

Что это даёт: при покупке сети с новым типом терминала (как в INC-8415) пишется или покупается только **плагин HAL**. Он раздаётся на планшеты через MDM (OTA-обновление), кассовое приложение не пересобирается. Вместо трёх недель — дни, а одинаковые модели терминалов в следующих сетях подключаются сразу.

## 4. Офлайн-режим и синхронизация после восстановления связи

**Как магазин работает без интернета.** Web POS построен по принципу local-first. На планшете всегда лежит актуальный снимок данных магазина: каталог, цены, правила промо, а также кэш карт лояльности с балансами на момент последней синхронизации. Каждый снимок имеет номер версии. Продажа за наличные не требует связи. PWA берёт цену из локального снимка и через HAL Agent отправляет чек на ККТ по USB. ККТ формирует фискальный чек и сохраняет его в фискальном накопителе. Покупатель получает чек сразу, а ККТ сама передаст документ в ОФД, когда появится интернет: накопитель блокирует кассу, только если документы не переданы в ОФД в течение 30 дней. Чек записывается в локальную **очередь исходящих событий (outbox)** — журнал только на добавление. У каждого чека есть уникальный идентификатор, созданный на планшете (UUID), время, номер смены и версия прайса, по которой он пробит. Карта лояльности в офлайне принимается: начисление баллов ставится в ту же очередь и проводится позже. Списание разрешено только в пределах кэшированного баланса и лимита (например, не более 500 баллов за офлайн-сессию). Так магазин не вешает табличку «без карт лояльности» (INC-8402), а риск двойного списания ограничен. Оплата картой зависит от канала связи терминала. Если терминал подключён через собственный GSM-модуль или магазин переключился на резервный 4G-канал, оплата картой тоже работает.

**Что происходит при восстановлении связи.** Sync Agent отправляет outbox в облако пакетами, строго по порядку, через API Gateway в Sync Service. Каждый запрос несёт ключ идемпотентности (UUID чека). Если связь оборвётся посреди отправки и пакет уйдёт повторно, Sync Service узнает уже принятые чеки по журналу и не создаст дублей. Чек удаляется из локальной очереди только после подтверждения от сервера. Принятые чеки превращаются в события `sale.completed` в Event Bus. Из них облако пересчитывает остатки, отправляет продажи в SAP через Integration Layer и проводит отложенные начисления в Loyalty Platform. Затем Sync Agent запрашивает изменения каталога, цен и промо: «отдай всё, что изменилось после версии N». Он получает только дельту, а не полный каталог, и атомарно переключает локальный снимок на новую версию.

**Как разрешаются конфликты.** Продажи — это неизменяемые факты, а не правки общей записи. Поэтому конфликтов при слиянии почти не бывает: чеки из разных касс и магазинов просто добавляются в журнал. Остатки считаются в облаке из потока событий, и временно отрицательный остаток после офлайна допустим: он попадает в отчёт для инвентаризации. Если цена изменилась, пока касса была офлайн, чек сохраняет цену, по которой фактически продан (фискальный документ изменить нельзя). Расхождение с новой ценой попадает в отчёт для коммерческого департамента. Для лояльности действует правило «сервер прав»: если офлайн-списание превысило реальный баланс, остаток уходит в небольшой минус и закрывается следующими начислениями. Мониторинг (MDM + Sync Service) отслеживает длительность офлайна. Если касса не синхронизировалась дольше заданного порога, Store Ops получает алерт заранее, чтобы не приблизиться к 30-дневному лимиту фискального накопителя и не продавать неделями по устаревшим ценам.
